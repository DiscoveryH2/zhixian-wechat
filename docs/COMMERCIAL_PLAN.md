# 知弦商业化执行计划

目标客户是通过微信处理客户沟通的销售、客服与客户成功团队。核心价值是减少遗漏、避免错误承诺、缩短客户上下文恢复时间。对话分析与回复生成只是入口，产品需要把证据、待办、客户状态和业务结果连接起来。

1.7.0 是跨平台与客户工作流的技术预览，尚不能标为企业级正式商用版本。它已经提供带证据的承诺扫描、人工确认的行动中心、归档检索、平台凭据存储和两端 CI。团队身份、细粒度权限、加密聊天库、商业授权服务和服务级别保障仍需下述工作。

## 第一阶段：两周内完成发布基础

- 固定 Windows 与 macOS 的支持矩阵，为每个微信版本准备合成数据库和媒体夹具；现阶段 Mac 使用导入数据，不宣传原生全库直读。
- 把捕获、数据源、凭据和发送封装为平台接口。控制器按业务拆成会话、媒体、行动、自动回复服务，保留 Qt 桥接的兼容契约；先补契约测试再移动代码。
- 补齐数据库迁移与恢复策略、损坏文件恢复、磁盘满、代理错误、网络中断、模型超时和退出中断测试。引入 Ruff 与类型检查，逐模块清理，保留协议、线程与许可相关注释。
- 给 macOS 加 Developer ID 签名与公证，Windows 加代码签名。验证升级、回滚和数据备份；发行包须有 SBOM、许可证、校验和与来源记录。
- 建立脱敏错误编号和本机诊断导出，记录版本、平台、模型路由类型与失败阶段，不记录消息、联系人、密钥或媒体。用户明确提交后才上传诊断。

验收：两端安装、保存密钥、导入、检索、分析、媒体、行动和退出各完成一轮实机验收；升级失败可回滚；未通过的平台不能发布为正式支持。负责人建议：桌面开发 1 人、测试 1 人、发布维护 1 人。

## 第二阶段：四周内把行动变成业务闭环

1. **承诺账本与矛盾提醒**：从消息中提取“谁答应了什么”，保留原文与消息 ID。检测后续对话中的条件变化、时间冲突和履约证据，提示用户核对。已有承诺扫描只生成提案，接下来加状态流转、合并去重与到期提醒。验收是每项动作都可回到原文，误判可纠正，绝不由模型单独改写事实。
2. **客户记忆变更审阅**：模型提出“联系人事实新增/更新/冲突”，用户确认后写入，保留来源和生效时间。报价、预算、联系人角色等信息过期后须复核。这样客户背景不会变成无法追溯的模型记忆。
3. **会前恢复包**：选择客户后生成近期变化、未解决问题、我方承诺、风险点和需要核对的事实；每条连回聊天证据。把准备下一次沟通从翻记录变成审阅一页。
4. **跨会话项目线索**：用户明确绑定相关私聊与群聊，发现同一项目的阻塞、重复沟通与责任空档。不同来源和同名客户保留独立身份，绑定有撤销和审计记录。

先选择 5–10 个试点席位，记录用户修正率、任务完成率和查找上下文耗时。优先修正错误行动与遗漏，不以聊天次数或模型调用量作为成功指标。

## 第三阶段：六到八周内验证付费版

- 建租户、成员与角色模型，提供可撤销的来源授权与审计。企业控制可使用的模型、成本上限、导出权限和数据保留期限。
- 聊天、笔记和行动数据使用受系统密钥保护的加密库；备份、导出与删除有清晰范围。默认不把整库上传，模型只接收显式任务所需的有界上下文。
- 做模型调用预算、超时与重试策略、请求优先级、失败恢复和用量核对；不可把发送状态不明的消息重试。商业服务支持客户自带 Key，并将软件席位费与模型用量分开呈现。
- 接入支付/发票、许可证与席位管理、离线宽限期和撤销。验证是否愿为承诺与跟进闭环付费，再决定私有部署、行业模板和 CRM 接入的优先级。
- 核对 MIT 上游归属、Qt/PySide 的 LGPL 分发义务、字体与运行组件许可证，以及模型服务条款。语音、联系人和客户数据的授权需进入真实产品流程，不能靠 README 代替。

验收：租户隔离测试通过；日志与遥测不含客户正文；密钥轮换、撤销、备份恢复、导出删除均有测试；客服能根据错误编号定位阶段。商用发布需要组织明确承接运维与支持。

## 更有辨识度的产品能力

| 能力 | 用户得到的结果 | 技术实现与验收 |
| --- | --- | --- |
| 沟通前的事实检查 | 发出报价或承诺前发现与历史说法冲突 | 将草稿中的关键事实与经确认的客户记忆核对，给出原文差异；允许“无法核实” |
| 跟进时机实验 | 知道哪些跟进方式更适合自己的客户 | 只使用用户选择的业务结果做离线统计与试点；区分相关性和因果，不输出伪精确的人际评分 |
| 客户旅程阻塞图 | 找到卡在谁、哪个问题、哪项承诺 | 用户确认项目绑定，聚合未解决问题与行动状态，提供可解释的证据路径 |
| 上下文交接包 | 同事接手客户时减少信息丢失 | 生成可编辑、带权限范围和原文引用的交接摘要，先预览再导出到 CRM |
| 沟通沙盘 | 在发送前练习几种表达与可能分歧 | 用明确标记的模拟场景训练用户，不冒充真实客户，也不把猜测写进客户档案 |
| 朋友圈关系触点 | 基于关系背景选择点赞、评论或私聊 | 采用真实动态和已确认聊天背景；公开草稿不携带私聊全文，用户决定是否发布 |
| 团队复盘教练 | 复盘承诺是否兑现与问题是否闭环 | 聚合经授权的行动结果，支持人工解释与纠错；不凭模型推断员工心理或绩效 |

数字分身、语音复刻和聊天记录导出可以作为后续组件，但它们本身不能证明商业价值。更值得形成壁垒的是可追溯的客户记忆、可靠的承诺账本、跨会话业务图和经过试点验证的沟通闭环。

## 工程指标与回归

这些是下一阶段的目标，尚不是 1.7.0 已达到的承诺：界面交互 P95 小于 100ms；首屏会话元数据 P95 小于 500ms；百万条本地索引在预热后常见查询 P95 小于 1s；模型请求有预算与取消能力；任务和模型并发不会阻塞界面线程。

每次发行运行跨平台单元/契约测试、合成 Qt 桥接测试、10 万/100 万条数据基准、打包启动与恢复测试。Windows 微信正向发送和 macOS 原生读取分别建立真实版本验收表，不能以合成数据、UI 截图或 API 请求成功替代送达和数据兼容性验证。将失败注入、修正率和性能回归设为发布门槛。
