# 知弦路线图：从回复助手走向对话决策台

知弦接下来要解决的，是从沟通记录中找出**有依据的事实、尚未完成的事和可以承担的下一步**。候选回复仍由用户选择与发送；更多历史、更强模型或更主动的提示，都不改变这个边界。

本页分开列出 v1.2 的现状和后续目标。下文的性能、质量与覆盖率数字是**计划中的验收门槛，不是已经测出的成绩或上线承诺**。每个阶段必须先提供可复现验证，再决定是否发布。

## v1.2 已具备的入口与限制

| 能力 | 当前边界 |
| --- | --- |
| 文字对话辅助 | 最简配置只需 Jev Key、Base URL、模型名；OpenRouter 默认可同 Key 起草回复，其他判断服务可先只用判断 |
| 会话目录与历史 | 已收集 OCR 会话、用户主动导入的 ChatLab、运行中的兼容 WeFlow；首批列表和后续历史分开加载 |
| ChatLab 归档 | 支持 JSON / JSONL 与 SQLite 索引；只覆盖实际导入的内容，归档明文保存 |
| 图片与语音 | 必须拿到真实媒体字节，按用户选择理解图片或做 STT；本地转写需额外依赖和模型 |
| 朋友圈建议 | 手动提供动态或读取 WeFlow API；可以建议点赞、公开评论、私聊或不回应，不执行互动 |
| TTS 与声音复刻 | 未实现，不应把语音转写入口当成文字朗读或声音克隆 |

没有运行中的 WeFlow，也没有用户提供的记录，就不能读取全部微信。OCR 的 `[图片]` / `[语音]` 标签不等于实际文件；朋友圈缓存里的零散图片不能恢复可靠的作者、时间与评论。API Key 使用 DPAPI，不意味着聊天归档也已加密。

## 先补齐可验证的数据底座

下一轮优先让数据范围、加载进度和删除行为都可检查，而不是继续增加会让用户误解的入口。

| 工作 | 交付内容 | 验收门槛 |
| --- | --- | --- |
| 大归档浏览基准 | 可公开重建的合成数据：1 万会话、100 万条消息；记录测试机和完整测试命令 | 在固定的 Windows 11、6 核 CPU、16 GB 内存、SSD 基准机上，本地首屏 20 条元数据 P95 ≤ 800 ms，下一页 P95 ≤ 300 ms；模型与网络耗时单独报告 |
| 可取消导入 | 导入进度、取消、异常回滚、重复文件识别与明确结果 | 合成 500 MB JSONL 导入额外峰值内存 ≤ 250 MB；取消请求在 2 秒内被处理；重复导入不增加相同消息条数 |
| 可解释的范围 | 每个列表展示 OCR / 导入 / WeFlow 来源、已加载数量和缺失能力 | 离线、Token 无效、接口缺失、空导出四类测试均不得显示“已读取全部微信”；失败后的来源切换不混用旧游标 |
| 归档生命周期 | 按归档删除、容量统计、媒体引用失效提示、可选加密索引方案 | 删除后查询结果与索引计数一致；原始导出不被误删；重启后保持删除状态；加密迁移可失败回滚且不遗留明文临时副本 |
| 媒体权限与成本 | 分开呈现原件可用性、本地/联网处理模式和提交范围 | 未选择处理的媒体出网请求数为 0；缺原件时不调用模型；格式不支持时不生成替代“转写”或“看图结果” |

这些指标先用于合成环境回归。真实微信版本、DPI、主题、导出来源与外部 API 的兼容性另外记录，不能用本机模拟结果代替实测结论。

## 阶段 A：带证据的关系与事件图谱

将用户选择的对话组织成 **人、事项、承诺、时间、证据消息**，回答“上次约定了什么”“这个决定后来改过吗”时，给出可跳回的原文和缺失信息。

不把所有聊天压成一个无法核对的长期摘要。先提供本地全文检索与消息引用；语义检索是单独可开的增强项。两个联系人名字相同，只能提示可能关联，不能自动合并。

**验收门槛：**

- 使用至少 200 个合成或用户自愿标注的问题，覆盖同名联系人、群改名、转发、撤回和证据删除。
- 每条展示为事实的结论都附来源消息 ID；引用解析成功率为 100%，找不到来源时降级为“依据已不可用”。
- 人工评审的事实支持率目标 ≥ 95%；无依据但被表述为事实的结论必须列为发布阻断问题，不用“置信度”掩盖。
- 删除某归档后，其原文不再进入检索或模型上下文；既有答案中的失效引用明确标记。

**能形成的产品：** 用户整理的是一组可复查的“对话证据”，而不是助手对关系的单方面记忆。

## 阶段 B：承诺与跟进台

从“我周五发版本”“等你确认后再付款”中提取事项、责任人和条件，形成待确认卡片。只有用户接受后才进入跟进队列；提醒出现时，同时展示原话和之后是否已经履行的证据。

承诺状态至少区分“待确认、已确认、等待条件、已完成、取消、依据不足”。对模糊日期不猜截止日，对他人的要求不直接当成自己的承诺。候选回复如果新增了时间、金额或责任，也要标出这些尚未确认的承诺。

**验收门槛：**

- 在至少 300 条标注片段上分别报告明确承诺、条件承诺和非承诺的精确率/召回率；进入自动建议队列的精确率目标 ≥ 95%。
- 连续转述、引用和同一承诺的重复确认不创建重复卡片；20 种约定变更用例均保留版本与原文引用。
- 所有提醒需要用户确认启用；关闭后不再创建系统提醒，模糊时间不产生臆造的截止日期。
- “已完成”必须来自用户确认或可展示的后续证据；模型猜测只能标为待核对。

**能形成的产品：** 助手帮助兑现对话里的约定，也能在起草下一句时提醒用户不要承诺做不到的事。

## 阶段 C：回复方案与公开边界检查

同一段对话可以先选择不同的行动方案：核对事实、承认已确认的问题、提出可执行安排，或先不回应。每个方案列出依赖的证据、需要补问的信息、草稿新增的承诺，再给出表达方式。

对朋友圈和群聊增加“公开边界检查”：用户看到的不只是某条回复分数更高，而是它是否引用了私聊细节、假定了关系亲密度，或加入了动态中没有公开的信息。用户修改草稿后也可重新检查，不强迫重新生成整段文字。

**验收门槛：**

- 至少 100 个隐私与事实诱导回归样本；公开评论的生成请求中私聊全文出现次数为 0。
- 草稿中的新增日期、金额、人物和行动承诺可逐项核对；引用不存在的事实时阻止直接作为推荐方案展示。
- 缺失模型分数时保持未知；不把意图判断当成真值，也不把排序概率解释为对方接受回复的概率。
- 在可选的本机反馈中记录“采用、编辑、放弃”的真实操作，并分别统计事实错误与隐私错误；不将未经用户确认的发送结果伪装成效果评估。

**能形成的产品：** 用户能比较做法、检查代价、编辑语言，最后仍由自己承担沟通决定。

## 阶段 D：群聊决策账本

围绕一个事项保留“提出问题 → 备选方案 → 决定 → 负责人 → 后续变更”。同一事项可以出现在多个被用户选中的群中，但系统只提出关联建议，避免将私人讨论直接带入另一个群。

有分歧时保留原文和未解决的问题，不把多数发言压缩成“大家一致同意”。无法确认发言人的 OCR 文本不得自动分配责任。

**验收门槛：**

- 至少 100 段多方讨论，人工标注决定、负责人、日期和反对意见；每个被输出的字段都附独立证据或“未确定”。
- 决定修改、负责人转移、引用转发和反对意见四类场景均有可重复回归样例。
- 跨群合并前显示来源范围并要求用户选择；未选中的会话不进入该事项的上下文。
- 导出决策记录时，允许只保留已确认事实与引用编号，默认不附整段私聊。

**能形成的产品：** 团队讨论拥有可追溯的结果，而不仅是一份容易遗漏异议的群聊摘要。

## 阶段 E：主动沟通队列与上下文预算

把可用会话整理为“需要行动、等待对方、仅通知、依据不足”等队列。排序理由来自用户优先级、明确问题和已确认承诺，不根据互动频率催促社交。

每次调用前可查看即将提交的上下文范围：哪些消息、哪条笔记、是否包括媒体、为什么需要它。用户可以移除某段背景，观察建议如何变化；这也让模型用量有边界。

**验收门槛：**

- 在合成 1 万会话目录中，界面先显示元数据，后台预热默认不超过最近 5 个会话的单条摘要；不因打开队列批量提交全文。
- 每条队列项有可核对的排序原因；用户纠正分类后，本机规则即时生效，不需要再调用模型。
- 请求账本区分判断、起草、排序和媒体处理；服务未返回用量时标为未知，不估算成真实账单。
- 支持每会话预算与全局暂停；达到预算后停止新模型请求，在途任务有明确取消或结束状态。
- 朋友圈建议允许“不互动”成为正常结果，不创建自动点赞、评论或批量私聊任务。

## 暂不作为承诺的功能

TTS 朗读可作为后续可访问性方向，但当前未实现；语音复刻、数字分身替人社交、自动发送和自动朋友圈互动不属于上述路线的发布承诺。CipherTalk 插件桥接可以扩展数据来源，但必须先验证事件、分页和身份稳定性，不能把“发现安装目录”当成“已经取得完整记录”。

每个阶段发布时同时给出实现范围、验证方法、未通过的门槛和已知限制。未完成的项目继续留在路线图，不提前写成产品能力。
